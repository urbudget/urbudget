## Confirmed findings

### R1 — P1: Hold the edit lock throughout installation on close

Location: [useBudget.ts:398](C:/Users/Admin/Documents/GitHub/urbudget/.claude/worktrees/ios-sync-iap-c3bc73/desktop/src/useBudget.ts:398), Arabic branch. The equivalent `await task()` is at line 400 on the auto-update branch.

The new close handler saves with `prepareExit()`, sets `updateReadyToClose`, and awaits the Store update. It never acquires `operationRef` or sets the operation state for this path. The ordinary manual-install path does acquire that lock through `exclusive()`.

While the Store request is pending, the window remains interactive: `edit()`, undo, and other operations can proceed. When the request returns—even on failure—the handler destroys the window without saving again. A second close request is also allowed immediately by `updateReadyToClose`. This can terminate with new changes unsaved, or while the asynchronous recovery write is still pending.

**Reproduced:** start `useBudget`; set an exit task backed by an unresolved promise; invoke the captured close handler; edit the budget while the task waits; resolve the task. At `destroy()`, `dirty()` is `true`. The regression assertion expected `[false]` and received `[true]`.

**Required correction:** hold the same edit/operation lock used by manual installation from the save through update completion and destruction. Ensure the shutdown bypass is enabled only while that lock is held. Cover a deferred update, attempted edits/undo/budget switch, a second close, and an update failure.

### R2 — P1: An unfinished bank import does not prevent automatic restart

Location: [App.tsx:397](C:/Users/Admin/Documents/GitHub/urbudget/.claude/worktrees/ios-sync-iap-c3bc73/desktop/src/App.tsx:397), Arabic branch, particularly the safety predicate at lines 400–406.

The predicate checks budget dirtiness, cloud sync, dialogs, `planningEditor`, and the focused element. It does not check `importing`, even though the bank file, edited session, and review choices live in that in-memory state. Import edits do not make `model.dirty()` true, and the import page is neither a modal nor a register/planning editor.

After working on an import, focus a button or another page and leave the app in the background. A downloaded update can restart the app after the idle interval, discarding the pending import and its review work. The same class of omission should be checked for the assistant's unsent draft and active work; that state is also separate from the budget.

**Reproduced on the actual Arabic App:** open Everyday account → Import, select `pending-review.pdf`, verify that the file remains displayed, and blur the input. Capture the real `safe` callback passed to `useAutomaticUpdate`. It returns `true`; the regression assertion expects `false`. The missing import-state check also applies to CSV sessions and their edited/reviewed choices.

**Required correction:** include every draft/operation that cannot survive restart in the safety decision, starting with an unfinished import. Test both while the import page is visible and after navigating away while the import remains pending. Do not rely on which element happens to retain focus.

### R3 — P2: Store consent cannot be requested after silent permission changes

Locations: [updates.ts:233](C:/Users/Admin/Documents/GitHub/urbudget/.claude/worktrees/ios-sync-iap-c3bc73/desktop/src/updates.ts:233) and [updates.rs:332](C:/Users/Admin/Documents/GitHub/urbudget/.claude/worktrees/ios-sync-iap-c3bc73/desktop/src-tauri/src/updates.rs:332), Arabic branch. Also present in PR #3.

Once a Store download returns `ready`, `silentStore.current` stays true. The native apply command checks permission again and can return “Windows needs your permission … Use Install Store update in Settings.” The frontend catch only sets the error; it leaves both the silent flag and `ready` unchanged.

Every subsequent click therefore invokes `apply_store_update` again, rather than the consent-capable `install_store_update`. Settings still says “Restart to update”; “Check now” is hidden while an update is available. Changing to a connection/settings state that requires consent leaves the user stuck in this retry path until a later check or relaunch resets it.

**Reproduced:** mock Store check as available and download as `ready`; make `apply_store_update` return the native permission-required error; press install twice. `install_store_update` is never called.

**Required correction:** distinguish consent-required from other install failures, invalidate silent readiness, and expose an explicit manual consent action. An automatic/background attempt must not unexpectedly open a permission prompt. Test the transition from downloaded/silent to consent-required and the subsequent manual install.

### R4 — P2: Recent income without an explicit marker still inherits an older expense category

Location: [payees.ts:60](C:/Users/Admin/Documents/GitHub/urbudget/desktop/src/payees.ts:60), current uncommitted keyboard work.

The revision handles an explicit `unassigned: true` marker, but still drops positive null-category transactions without that marker. Those are valid income to Unassigned in the existing accounting model: `splitRole()` treats a nonnegative null-category amount as income independently of `leftUnassigned()`.

Example payee history, oldest first:

| Date | Amount | Category |
| --- | ---: | --- |
| September 1 | -50.00 | Gifts |
| September 5 | +2,500.00 | null, no explicit marker |
| September 10 | +2,500.00 | null, no explicit marker |

`payeeHabits` discards both recent income categories and reports Gifts as the sole category. `onPick` then prefers that result over `payeeIndex`'s latest null category, and smart Tab can skip the category entirely. The next salary is saved into Gifts instead of Unassigned.

**Reproduced with a component test:** select Employer, Tab, enter an inflow of 2,500, and Save. Current code saves `categoryId: "gifts"`; the same test using `TransactionEditor` from current main saves `categoryId: null` and passes. This is the remaining part of the earlier income-category finding, not a new objection to intentional Unassigned income.

**Required correction:** distinguish uncategorized spending from positive income when deriving category history. Cover legacy/imported null-category income as well as explicitly marked Unassigned income. Keep the regression at the component level so it checks the actual saved category and navigation behavior.

The other earlier keyboard cases now have fixes: pasted signed expressions are restricted to plain-amount sign switching; deleted payee defaults are filtered; Account participates in arrow navigation. The current 35 targeted tests pass, including explicitly marked Unassigned income.

## Integration and tag blockers

Read-only three-way merge checks used the actual merge bases. No branches were merged or checked out.

- PR #3 and PR #4 each merge textually into current main without conflict. PR #4 contains the updater feature already; follow the declared #3 → #4 order and carry the updater fixes into the Arabic result.
- Phone editing versus current main conflicts in `docs/FOLLOW-UPS.md`.
- Phone editing versus Arabic conflicts in `android/app/src/main/java/app/urbudget/nativeapp/ui/AssistantScreen.kt`, `ios/UrBudget/Screens/Assistant/AssistantProposalCard.swift`, and `docs/FOLLOW-UPS.md`.
- Keyboard versus Arabic has nine conflict hunks in `desktop/src/TransactionRow.tsx` and one in `desktop/src/register.css`. This needs semantic integration: keyboard routing uses English labels as identifiers, while Arabic translates those labels. Prefer stable field identifiers and separately localized accessible names; verify Tab, arrows, focus, and split-amount switching in Arabic.
- New phone edit controls have no matching Arabic catalog entries yet. Examples absent from the iOS catalog include “Use the assistant's version”, “Change %@”, “Category for %@”, “Amount for %@”, and “Changed by you”. The Android additions also contain literal English text. Localize the newly added behavior during integration, including partial-count labels and accessibility text.
- Source versions are **desktop 1.0.9, Android 1.0.0, iOS 1.0.0**. Running `node scripts/versions.mjs --tag desktop-v1.0.10` fails because desktop is still 1.0.9. After the fixes and integration, set desktop to 1.0.10 through `node scripts/versions.mjs desktop 1.0.10`, finish its changelog, and commit the synchronized versions before tagging.
- The desktop release trigger is **`desktop-v1.0.10`**. A bare `1.0.10` or legacy `v1.0.10` does not match this workflow's push trigger. A desktop tag builds desktop installers; it does not publish the phone applications. Phone releases have separate tags and workflows.
